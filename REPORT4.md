## Вопросы

### 1

Открываем нужный эксперимент и Run, связанный с версией модели. Сохраняем `run_id`, `experiment_id`, параметры обучения, а также Git commit SHA и MD5 hash датасета.

Чтобы восстановить код, по SHA возвращаемся к нужной версии проекта, включая `train.py`, `pyproject.toml` и `uv.lock`:

```bash
git checkout <git commit>
```

Чтобы восстановить данные, используем соответствующие `.dvc`-файлы из этого коммита:

```bash
uv run dvc checkout
```

Затем нужно установить зависимости:

```bash
uv sync --locked
```

Затем запускаем обучение с параметрами из MLflow, по аналогии с:

```bash
MLFLOW_TRACKING_URI=http://mlflow.localhost uv run python -m churn.train
```

### 2

В образе храним только указатели на данные, потому что датасет может быть тяжёлый. Кроме того, хранение данных через DVC позволяет версионировать их отдельно от кода.

Если выполнить `git push` раньше `dvc push`, в Git появятся указатели на данные, которых ещё нет в хранилище. При попытке скачать их через `dvc pull` в поде возникнет ошибка, и обучение или валидация не смогут выполниться.

Это будет видно в графе соответствующего DAG в Airflow на задаче `validate`.

### 3

Бинарные проверки: уникальность id, отсутствие пропусков, допустимые значения Geography и Gender, диапазоны CreditScore, Age, NumOfProducts, Tenure, Balance, EstimatedSalary, Excited.

Проверки с порогом: минимум 10 000 строк в датасете и доля ушедших клиентов Exited от 10% до 30%.

Чтобы подобрать пороги, смотрел на распределения параметров датасета. По-хорошему, нужно смотреть на распределение признаков за всю историю по собранным данным.

Если пороги слишком строгие, то валидные данные могут не пройти, например, если распределение признака изменилось естественным путём.

### 4

Pandera проверяет валидность данных для обучения моделей. Pydantic-схема проверяет валидность данных, приходящих на вход сервису. Нужны обе, так как они проверяют данные на разных этапах.

### 5

Airflow предназначен только для того, чтобы оркестрировать задачи. Сам процесс обучения выполняет под с образом сервиса, с тем же кодом и зависимостями.

Выкатка новой модели не требует пересборки образа, потому что его код не меняется. Меняется только чемпионский алиас в MLflow. Чтобы в подах появилась новая модель, достаточно их перезапустить.

### 6

- **Метрики про инфраструктуру:** рестарты контейнеров сервиса.
- **Метрики про сервис:** версия модели в подах, запросы к `/v1/predict` за 5 минут, задержка `/v1/predict`, запросы в секунду, размер батча (p50 / p95).
- **Метрики про модель:** распределение score за 15 минут, доля клиентов с прогнозом «уйдёт», распределение признаков.

`request_id` не стоит класть в метку Prometheus, так как данный параметр имеет уникальное значение для каждого запроса. Из-за этого Prometheus перегрузится.

### 7

Во время выката новой модели поочерёдно создаются новые и убиваются старые поды, что соответствует стратегии Rolling Update. Благодаря этому запросы продолжают обрабатываться во время обновления.

`preStop` позволяет поду перестать принимать запросы перед завершением и завершить уже обрабатываемые. Без него, при остановке старых подов, видели ошибки выполнения запросов.

### 8

Самый вероятный отказ — дрейф модели. Первый сигнал этого можно будет заметить при помощи мониторинга распределения доли клиентов с прогнозом «уйдёт». Первое, что я сделаю — сравню распределение ключевых признаков в обучающих данных и запросах из таблицы по PSI. В случае подтверждения существенного отклонения нужно будет проверить источник данных, а также, при необходимости, откатить модель на предыдущую версию. Когда появятся размеченные данные, запущу переобучение модели.
